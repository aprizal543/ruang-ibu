#### Migration compatibility audit

`migrations/0001_questions.sql` uses standard SQLite `CREATE TABLE IF NOT EXISTS`, `CHECK`, `UNIQUE`, foreign-key actions (`CASCADE`/`SET NULL`), indexes, and `json_valid`; Cloudflare D1 documents SQLite compatibility, JSON functions, and these foreign-key capabilities. Its leading `PRAGMA foreign_keys = ON` is redundant on D1: foreign-key checks are enabled for D1 queries and migrations and cannot be toggled inside a migration transaction. It should not be treated as the mechanism enabling constraints; the declared foreign keys are what enforce them. The migration remains unchanged. Backend tests have exercised the schema against local SQLite, but no D1 remote migration compatibility run has been performed.

Safe future order, after explicit owner authorization: verify the Pages Preview binding and exact account/resource in Dashboard; back up/check recovery readiness; run the read-only `migrations list` with `--remote --env preview` and confirm the name/UUID; then, only if explicitly authorized, apply interactively with `migrations apply ... --remote --env preview` without `--yes`; finally inspect migration status and schema metadata. Never run this sequence against Production. Cloudflare documents D1's SQLite and foreign-key behavior in [SQL statements](https://developers.cloudflare.com/d1/sql-api/sql-statements/), [foreign keys](https://developers.cloudflare.com/d1/sql-api/foreign-keys/), and [migrations](https://developers.cloudflare.com/d1/reference/migrations/).

### E. Protect the Preview at Cloudflare Access

Recommended staging gate: enable the Pages project's **Preview deployments Access policy** so Preview deployments are private as a whole. This intentionally protects public pages as well as `/admin`; authorized testers can still inspect the site. Cloudflare documents this Pages setting as applying to Preview deployments, not the project's production `*.pages.dev` hostname or custom domains.

1. In **Workers & Pages > `ruang-ibu` > Settings > General**, locate the Preview deployments access policy control and enable it for Preview deployments.
2. In **Zero Trust > Access controls > Applications**, inspect the application created/used for the Preview policy. Confirm the Access policy is an **Allow** rule with **Include > Emails** listing only the specifically approved operator addresses. Do not use `Everyone`, a broad email-domain rule, or a policy that allows all one-time-PIN users.
3. Verify the policy covers both the current hash deployment and the branch alias shown in step A. Cloudflare Pages Preview protection is preferred here because it follows the Preview deployment set; do not assume a manually entered path app covers future hash hosts.
4. Copy the application **Application Audience (AUD) Tag** from its Additional settings. Record the exact team origin shown by Zero Trust. Set `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD`, and `ADMIN_EMAILS` only in the Pages **Preview** environment.
5. Keep `functions/api/admin/_middleware.ts` enabled. Access blocks the request at the edge; the Function still verifies the signed assertion, issuer, audience, expiration and email allowlist.

The project-wide Pages Preview policy is stricter than path-only access: it requires login for `/`, education pages and APIs on the Preview as well. This avoids a gap between a hash hostname and a branch alias. Production remains public because the Pages Preview policy does not apply to the Production hostname. Do not add the Production hostname to the Preview policy.

If the owner later chooses path-only Access instead, treat that as a separate reviewed change: Access applications must match each actual Preview hostname and the exact paths `/admin`, `/admin/*`, `/api/admin`, and `/api/admin/*`; a wildcard path does not cover its parent path. Re-test each path and every current hash/alias. Do not configure a broad `*.pages.dev` policy.

**Verify before redeploy:** unauthorized requests to the hash URL and branch alias receive Access login/deny before app content; an approved operator can load the Preview; the Production public homepage remains reachable without Access. Authenticated calls then exercise the Function JWT verifier. If Access config is missing in Functions, the API must return a generic 503 after the edge gate, not skip authentication.

## 5. Acceptance test plan (synthetic records only)

Run the tests in this order on the protected Preview and record commit SHA, actual hostnames, HTTP status, response headers, and redacted result. Do not record tokens, secrets, full emails, or question text in logs/evidence.

| Check | Procedure | Pass condition |
|---|---|---|
| Preview host coverage | Test unauthenticated and authorized visits to the current hash URL and branch alias | Both are blocked for unauthenticated users and accessible to the approved operator; production public host remains public |
| Unauthorized admin | Request `/admin`, `/admin/`, `/admin/questions`, `/api/admin/summary`, `/api/admin/questions` without Access session | Edge blocks/redirects; no admin payload or question data |
| Function JWT gate | With Access edge session, call the admin API with real Access-issued assertion; then separately verify missing/malformed config in isolated local tests | Valid allowlisted JWT passes; Function rejects invalid/missing JWT or returns `admin_auth_not_configured` when required Preview vars are absent |
| D1 Preview binding | Start from known empty Preview DB, submit a synthetic test question, then view admin summary/inbox | Only the Preview database changes and the same synthetic question appears through the dashboard API; verify Preview DB identity again in Dashboard |
| Pending privacy | Submit a pending synthetic item with synthetic optional email; call public GET for its article | Pending row is absent; response has `Cache-Control: no-store` and no email/original text/internal metadata |
| Invalid Turnstile | Same-origin POST with deliberately invalid token while all required Preview settings are present | `403 verification_failed`; no question inserted. This attempt counts toward the IP rate limit |
| Approve and sanitize | In dashboard, edit public name and public question to remove all personal/health identifiers; approve | Admin row status becomes approved; only edited public fields appear via public GET; original/email remain absent |
| Answer | Enter a manually authored synthetic educational answer in dashboard | Status becomes answered; public GET shows approved public question and answer; no email or original text |
| Rate limit | Use fresh, single-use valid Turnstile tokens from one real test source IP for three posts, then a fourth | First three can be accepted as pending; fourth returns 429. Invalid attempts also consume quota, so run this check last or from a separate controlled tester/network. Never spoof `CF-Connecting-IP` |
| Service worker/cache | Inspect Cache Storage and network headers while loading public GET, admin summary, `/admin`; repeat offline navigation | No API response/private body is cached; `/admin` does not render from offline SPA fallback; public static app assets behave normally |
| Public regression | Browse `/`, `/terapi`, a detail article, `/hamil`, `/bersalin`, `/relaksasi`, `/evaluasi`; test M1 Back/scroll, M2 source disclosure and photos | Public routes work for authorized Preview reviewer, no console errors or overflow, evaluation remains ephemeral |
| Cleanup | Use the admin individual-delete action on each synthetic test record after evidence is captured | Synthetic Q&A content removed; minimal delete audit record may remain. Do not call retention purge |

The current API enforces a fixed hourly limit of three attempts per trusted `CF-Connecting-IP`, and increments before Turnstile verification. Plan the invalid-token and valid-submission tests around that ordering. Do not send an `X-Forwarded-For`/`CF-Connecting-IP` override from a client; the edge-provided `CF-Connecting-IP` is the value used by Functions.
